# 试玩复核

## 1. 汇总

```bash
gh api "repos/{owner}/{repo}/milestones?state=all" --jq '.[] | "\(.number) \(.title) open=\(.open_issues)"'
gh issue list --milestone "<里程碑>" --state all --json number,title,state
```

除复核 issue 本身，其余 issue 都应已关闭；没关的列出来，问用户是继续复核还是先完成。

## 2. 自动化复核

`npm test && npm run build && npm run e2e`，逐张看截图，对照《游戏方向》各节记录不符之处。

`tests/shots/` 不入库。挑 3–6 张能说明结论的截图复制到 `docs/04-审计/截图/` 下以迭代命名的子目录（如 `迭代1/`），在复核文档里用相对路径引用（这些是测试截图，不是游戏资产，不用登记 `assets/README.md`）。

检查《游戏方向》§11 待确认：仍有条目时列进复核文档，请用户本次确认；确认后按结论改正文并删掉条目。

## 3. 真人试玩

给出试玩方式（`npm run dev` 地址、或 PR 预览地址）和一份 5–8 条的试玩清单（对应本里程碑的验收）。请用户试玩后回答：

- 核心循环是否成立、哪里卡、哪里无聊；
- 清单逐条：通过 / 不通过 / 没试到；
- 设备与浏览器。

用户没法试玩时，文档里写明“仅自动化复核，真人试玩待补”，**不要编造试玩反馈**。同时在下一个里程碑的试玩复核 issue 里加一条“补测迭代 N 的真人试玩”，下次复核时一并完成。

## 4. 写复核文档

在 `docs/04-审计/` 取下一个编号，名称如 `0N-迭代N试玩复核.md`，按 `docs/00-文档规范.md` 写文档头，状态“已完成”；在 §8 索引登记。内容：

| 节 | 内容 |
|---|---|
| 1. 范围 | 里程碑、包含的 issue |
| 2. 方式 | 自动化（命令、截图位置）与真人（谁、设备） |
| 3. 结论 | 对照《游戏方向》逐条：符合 / 偏差 |
| 4. 问题 | 每条问题一行：现象、影响、建议、对应新 issue |

## 5. 新问题与收尾

用 `plan-issues` 的规则把问题拆成 issue（下一个里程碑或当前里程碑），在文档 §4 填上编号。按 `do-issue` 的流程提交复核文档 PR，正文 `Closes #<复核 issue>`。

复核 PR 里同时把《迭代计划》§1 本迭代的状态改为“已完成”。PR 合并后，仓库的 `milestone-close` 工作流会在里程碑没有 open issue 时自动关闭它；本地手动收尾或工作流没跑时：

```bash
gh api -X PATCH "repos/{owner}/{repo}/milestones/<编号>" -f state=closed
```
