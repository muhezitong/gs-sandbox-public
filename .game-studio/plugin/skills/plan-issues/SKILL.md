# 拆 issue

## 1. 读上下文

- `CLAUDE.md`：区域标签取值、里程碑命名、项目特有约定。
- `docs/01-设计/01-游戏方向.md`：需求是否在 §9 范围内、涉及哪些章节。
- `docs/03-计划/01-迭代计划.md` 与 `gh issue list --state open --limit 100`：避免重复，找依赖。

需求超出《游戏方向》范围时，先告诉用户，并把“更新《游戏方向》”作为第一个 issue。

## 2. 拆分规则

- 一个 issue 一个 PR，能独立完成、独立验证；做不完或混了多件事就拆开。
- 改数值或规则的 issue，要做的事里第一条是“改《游戏方向》§N”。
- 美术 issue 写明资产要登记到 `assets/README.md`。
- 每个 issue 都要有可检查的验收：单测、e2e 场景、截图或试玩现象。
- 依赖只指向本批或已存在的 issue。
- 新里程碑：最后一个 issue 是“迭代 N 试玩复核”，依赖本里程碑全部 issue。

## 3. 草稿确认

用表格给用户看：序号、标题（不超过 70 字符）、类型 / 区域 / 优先级、依赖（序号或 `#编号`）、里程碑，以及每个 issue 的验收要点。**用户确认之前不写入 GitHub。** 用户改了就重出草稿。

如果调用方已在指令中明确说明“草稿已确认、直接创建”，可以跳过等待。

## 4. 创建

里程碑不存在时，先在《迭代计划》§1 加一行（这个改动走一个文档 issue / PR，或在用户同意下与本次一起提交），再 `npm run setup:github` 同步里程碑。

按依赖顺序逐个创建，正文用 `.github/ISSUE_TEMPLATE/需求.md` 的结构（背景 / 要做的事 / 验收 / 依赖 / 参考），依赖写真实编号：

```bash
gh issue create -t "<标题>" -F <正文文件> -m "<里程碑>" -l "类型:<…>" -l "区域:<…>" -l "优先级:<…>"
```

最后列出创建的 issue 编号与链接。
